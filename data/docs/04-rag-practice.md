# RAG 实战笔记

## 一个最小可用的 RAG 由四步组成

1. **解析**：把 PDF、DOCX、Markdown 转成纯文本，保留页码/行号。
2. **切块**：按语义边界切成 500-1000 字的片段，块之间留 10%-20% 重叠。
3. **检索**：给每个块建索引，按相关度返回 top-k。
4. **生成**：把命中的块塞进 prompt，要求模型只依据材料回答并标注来源。

这四步里，**检索质量决定上限**，模型只决定表达。检索错了，再强的模型也只能一本正经地胡说。

## 切块的五个原则

- 块太大：噪声多，命中后模型抓不到重点，还浪费 token。
- 块太小：语义不完整，“它”指代不明。
- 按结构切：Markdown 按标题/段落，代码按函数，PDF 按页。
- 保留重叠：跨块的句子不至于被腰斩。
- 记录位置：没有行号/页码，引用就是假的，用户无法核对。

## 为什么第一版不用向量库

向量检索擅长语义相似（“报销流程”能命中“费用申请”），但需要 embedding 服务和向量库，成本和复杂度都上一个台阶。
BM25 是纯词频统计，零依赖、可解释、中文用字级 bigram 就能跑：

- “知识库”切成“知识 / 识库”，查询同样切，精确命中。
- 缺点是同义词不敏感：搜“缓存”不一定命中“cache”。

实用策略：**先 BM25 上线，收集真实 query，再决定要不要加向量召回和 rerank**。
不要一上来就搭 Pinecone + LangChain，最后发现 80% 的问题是文档没清洗。

## 引用怎么做才可信

1. 检索结果带唯一编号（cite），工具返回给模型。
2. system prompt 强制要求“每个结论后标 [n]”。
3. 服务端把编号和真实片段绑定，前端展示可展开的来源。
4. 模型编造编号时，前端点开找不到内容，用户立刻能发现。

引用不是装饰，是**让幻觉可被审计**。

## 评估 RAG 的三个指标

- **召回率**：该命中的块有没有进 top-k。构造 30 个问题人工标注。
- **忠实度**：回答里的每个论断是否能在来源中找到。
- **拒答率**：资料没有时是否敢说“不知道”。这一项最容易被忽略。

上线前至少跑 30 条真实问题；上线后把“点了踩”的问题回流成测试集。

## 常见失败模式

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 答非所问 | 查询和文档用词不一致 | 查询改写、同义词、混合检索 |
| 引用对不上 | 编号在多次检索间重置 | 全局引用登记簿，按 chunk 去重 |
| 答得太空泛 | 块太大或 top-k 太多 | 减小块、加 rerank、只留高分 |
| 把别的文档内容混进来 | 没做权限过滤 | 检索前按用户/空间过滤 |
| 扫描版 PDF 没内容 | 缺 OCR | 接入 OCR 或提示用户 |
