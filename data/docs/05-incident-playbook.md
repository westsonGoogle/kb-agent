# 线上故障排查手册（示例）

> 这是一份用于演示检索的运维手册，描述一个典型 Web 服务的排障顺序。

## 接口大面积 500

按这个顺序查，不要一上来就重启：

1. **看时间线**：监控上 500 是从几点开始的？和最近一次发布、配置变更、数据库迁移对得上吗？
2. **看错误分布**：是所有接口都 500，还是只有某个路由？全部挂通常指向依赖（数据库、Redis、下游 API），单路由挂更像代码 bug。
3. **看日志**：先 grep `ERROR` 和 `Traceback`，确认异常类型。`ConnectionRefused` 是依赖没起来，`Timeout` 是下游慢，`KeyError` 是数据问题。
4. **看资源**：CPU、内存、文件描述符、连接池。连接池打满会表现为“偶发超时”，不是 500。
5. **回滚**：如果确认和发布相关，先回滚止损，再慢慢定位。不要在线上边查边改。

## 接口变慢但没报错

- 先看 P99，不要只看平均耗时；平均值会被大量快请求拉低。
- 查慢查询日志和外部调用耗时，常见根因是 N+1 查询和同步调用外部 API。
- 检查连接池配置：`pool_size` 太小会让请求排队，表现像“网络慢”。
- 如果是 GC 导致的毛刺，看 GC 日志和堆内存曲线。

## 数据库连接耗尽

典型报错：`too many connections`、`remaining connection slots are reserved`。

处理顺序：

1. 统计当前连接数和来源 IP，确认是应用泄漏还是正常流量上涨。
2. 检查代码里是否有未关闭的 session（异常分支最容易漏）。
3. 临时提高上限只能止血，必须找到泄漏点。
4. 加连接池上限和超时，避免一个慢查询拖垮全部连接。

## 发布检查清单

- [ ] 数据库迁移可回滚，且在新代码之前执行
- [ ] 新配置有默认值，缺配置不会启动失败
- [ ] 关键接口有超时和重试上限
- [ ] 日志里不打印密钥、token、完整身份证号
- [ ] 回滚脚本演练过

## 事故复盘怎么写

只写事实和机制，不写“某人粗心”。模板：

1. 影响面：多少用户、多长时间、哪些功能。
2. 时间线：发现、止血、恢复、复盘。
3. 根因：直接原因 + 深层原因（为什么测试没拦住）。
4. 改进项：每项有负责人和截止时间，优先做能自动化的。

复盘的目标是让同类事故不再发生，不是找人背锅。
